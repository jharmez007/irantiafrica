# 21 — Transactional notifications
Trace: FR-NOT-001, NFR02/03/06; Q16. Required V1 events: **OrderPlaced and PaymentApplied** confirmations. Authentication verification/reset and guest-access messages are necessary security enablers. Processing/shipment/delivery/cancellation/return/refund emails are candidate transactional additions awaiting trigger/template approval, not automatically confirmed features. No marketing or abandoned-cart worker.

Order/payment transaction writes outbox event; relay dispatches job; handler inserts/claims NotificationDelivery with unique event_id + template + recipient digest. Render approved template from immutable order snapshots and minimal safe current contact. Provider adapter sends outside DB transaction, records provider message ID and result, retries known transient failures with bounded backoff. Required mail failure does not roll back payment/stock; alert and provide authorized account/guest status view.

Exactly one logical notification intent is enforced. Physical email exactly-once delivery cannot be guaranteed across an ambiguous provider timeout unless provider supports idempotent sends/query; record UNKNOWN and reconcile before retry where available. Residual duplicate transport delivery is disclosed rather than falsely claiming exactly-once external side effects. Provider selection should favor idempotency/status lookup and bounce events.

Keep security and commerce transactional queues prioritized separately from media work. Configure sender domain/authentication (SPF/DKIM/DMARC as provider requires), reply-to/support address and test delivery before launch. Respect hard-bounce handling for transport while providing alternative support access; never treat a bounce as order cancellation. Verify signatures on provider callbacks if adopted; they are operational email dependency callbacks, not additional business integrations.

Templates show stable order reference, itemized NGN amounts/tax, accurate payment state and safe canonical links. Order confirmation must say pending until verified payment. Never send passwords/card data/secret webhook payloads. Guest access link expiry and no-referrer/token-redaction controls follow [16](16-authentication.md). Store template/version and masked recipient metadata, not full email bodies indefinitely.

Tests: rollback emits no mail; duplicate job one intent; provider timeout uncertainty; failed delivery alert; confirmation contains separate tax and correct totals; guest link is scoped/expiring. Provider, language, exact optional triggers, retention and sender ownership are Q16 production/configuration decisions.

## Phase 3K implementation refinement — 2026-09-24

The explicit Phase 3K authorization selects the [12-event V1 matrix](../development/notification-matrix.md), superseding the candidate-only allocation above for those events. Existing journal names `OrderCreated` and `PaymentSucceeded` implement the conceptual OrderPlaced/PaymentApplied confirmations. [ADR-017](adr/017-committed-notification-relay.md) records the relay from durable committed journals, real source FKs, immutable delivery identity, bounded retries and UNKNOWN fencing. Historical order contact is authoritative, not current account contact. Guest recovery remains deferred per Phase 3G; no guest access link is emailed. Existing identity reset remains separate. See [operations](../development/notifications.md) for external provider/bounce activation gates and safe environment modes.
