# 16 — Authentication
Trace: FR-ACC-001/002/005, FR-RET-003, NFR01/03; ADR-008. **Select Laravel Sanctum first-party SPA cookie/session mode**, backed by PostgreSQL sessions. No browser JWT/localStorage token and no duplicate Next authentication database.

Browser uses a single canonical HTTPS origin. Reverse proxy routes /api/v1/* and /sanctum/csrf-cookie to Laravel. Sanctum stateful middleware and session guard protect API calls; configure trusted origin/hosts explicitly. CSRF bootstrap sets readable XSRF token; client sends X-XSRF-TOKEN with credentialed writes. Session cookie is Secure, HttpOnly, host-only, SameSite=Lax with narrow suitable path. CSRF cookie is necessarily readable but is not the session credential. No wildcard credentialed CORS. Proxy must strip untrusted forwarding headers.

Registration validates/normalizes email, hashes passwords with supported framework password hashing and creates no staff privileges. Email verification is recommended before sensitive account actions; guest checkout remains available. Required fields/verification enforcement await Q12. Login rotates session ID; logout invalidates session and CSRF state. Reset uses short-lived single-use hashed token, generic issuance response and session revocation after success. Password policy, throttling and breach/password-manager usability are reviewed with security acceptance; no secrets in logs.

Server Components may forward current request cookie to private Laravel only for authorized reads. No global cookie jar, user-data cache or token minting in Next. Authentication-changing endpoints are browser→Laravel so Set-Cookie reaches browser; RSC reads must not implement login/token rotation. Frontend visibility guards are UX only; every API query/mutation authorizes ownership and role.

Admin accounts are provisioned through owner-controlled invitation/provisioning, not public registration or a request field. Same identity store with granular role assignments; proposed mandatory MFA and recent reauthentication for role/refund/security changes. TOTP seed encrypted with external key; recovery codes hashed and one-use. No custom cryptographic implementation. Framework-compatible MFA integration/version must pass foundation security review before enabling; staff provisioning and recovery ownership require Q13 approval. Disabled users and removed privileges invalidate sessions or trigger authorization-version checks immediately; do not trust stale role claims.

Guest cart access and guest order access are distinct. Order access recommendation: cryptographically random emailed one-time capability, digest stored with order/scope/expiry; exchange through POST for a short-lived restricted HttpOnly session/capability cookie. Redact token URL/query from logs, use no-referrer and remove from URL immediately; token GET should show confirmation rather than consume on mail-link scanners. Grant only that order's status/return operations, not other orders sharing email. Reissue generic response after rate-limited request; validate token in constant time, atomically consume, rotate and bound expiry. Customer can return without creating an account. Matching email alone never automatically claims guest order history.

Throttle login/reset/verification/guest access by privacy-preserving account and network keys with safe global bounds; progressive delays and monitoring address brute force/credential stuffing. Session idle/absolute lifetimes are configurable with shorter staff durations; values need Q12/Q13 approval before launch. Never use IP binding as sole identity. Redis failure cannot disable protection: sensitive routes fail closed or use bounded database limiter fallback. Database/session outage fails auth closed.

Source: [Sanctum cookie SPA authentication and CSRF](https://laravel.com/framework/docs/13.x/sanctum).
