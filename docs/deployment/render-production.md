# Render production deployment — ultra-lean controlled pre-launch

**2026-10-04: configuration prepared, not provisioned. Phase 3O remains open.** The business owner approved [ADR-018](../architecture/adr/018-ultra-lean-production-deployment.md): one Frankfurt `1c-2g` Docker web service and one managed PostgreSQL 18 database. There is no separate staging environment, Redis/Key Value, Render worker or Render cron. Production will first run behind Basic Auth with Paystack TEST; no public/live launch is authorized.

## Runtime and data flow

`render.yaml` declares exactly one `web` service and one `database`, with auto-deploy off. The Docker image builds Node 24/Next standalone and PHP 8.5/Laravel, then runs unprivileged Supervisor with five foreground programs: Nginx, PHP-FPM, Next, one database queue worker and `schedule:work`. Nginx is the only public listener; it routes `/api/*` and `/sanctum/*` to loopback Laravel, the rest to loopback Next. HTTP health is `/api/v1/health`; run `php artisan app:readiness` privately to check PostgreSQL, `jobs` and database cache. Inspect Supervisor status and overdue scheduled/queued work separately. A repeatedly failing child can enter FATAL and needs an alert.

The pre-deploy command runs `php artisan migrate --force`. Never run `migrate:fresh` or UAT seeders in production. Active `jobs`, `failed_jobs`, `cache`, `cache_locks` and `sessions` migrations are required. `DB_URL` is injected from the Render database's **internal** `connectionString`; `DB_SSLMODE=require` is an explicit private-network provider exception, not certificate hostname verification. Confirm the actual TLS connection and private network on Render. Keep database ingress private. The first generated database role may have DDL privileges; plan a least-privilege runtime role and negative DDL test after bootstrap.

The worker runs:

```sh
php /app/backend/artisan queue:work database --queue=identity,default,transactional,media --sleep=3 --tries=3 --backoff=30 --timeout=60 --memory=256 --max-time=3600
```

`DB_QUEUE_RETRY_AFTER=90`; `after_commit=true`; failed jobs stay in PostgreSQL. Supervisor restarts normal `--max-time` exits. One worker means a running media job can delay an identity/payment job for up to its 60-second timeout. At idle, four queue probes every three seconds imply roughly 80 polls/minute; measure real query rate and claim latency before changing sleep. Do not promise exactly-once execution. Payment/refund transitions, inventory and notification delivery retain database uniqueness, leases, outbox/inbox and idempotency.

`CACHE_STORE=database`, `RATE_LIMIT_CACHE_STORE=database`, `SESSION_DRIVER=database`. Database locks cover media overlap and scheduler leadership. Each scheduled event has `onOneServer()`, and critical long-running scans retain `withoutOverlapping()`. Old and new Render containers may overlap during a deploy; the shared database mutex prevents duplicate scheduling, while domain idempotency protects effects. `schedule:work` is the sole scheduler. Hourly jobs delete expired cache/cache-lock rows and stale sessions. Monitor table size and vacuum on the small PostgreSQL plan.

Two PHP-FPM children are the initial limit. Approximate ordinary DB demand: two FPM requests, one queue worker, one scheduler child during minute execution, up to one spawned command and one operator shell = about six application connections, before idle/deploy overlap and provider overhead. Next calls Laravel over HTTP and opens no direct PostgreSQL connection. During two-container handover, allow roughly double the application connections. Verify against the purchased plan's actual limit. Do not enable persistent PHP connections without measurement.

Render's `maxShutdownDelaySeconds=240` allows the worker's 75-second grace and other children to stop. The local Podman image build, five-child Supervisor restart test and 1.68-second graceful stop passed against isolated PostgreSQL 18 with a delayed job preserved; see the [Phase 3O evidence](../development/phase-3o-report.md). A killed in-flight job can run again after its 90-second lease. Populated-data resource peaks, small-Postgres load and Render handover remain **NOT VERIFIED** until measured.

## Media, email and payments

Cloudflare R2 is the preferred private S3-compatible bucket. Set `CATALOG_DISK=s3`, `FILESYSTEM_DISK=s3`, `CATALOG_UPLOAD_TRANSPORT=proxy`, `AWS_DEFAULT_REGION=auto`, `AWS_USE_PATH_STYLE_ENDPOINT=true`, bucket/endpoint and scoped credentials privately. R2 does not support the existing S3 browser POST policy or object ACL headers, so the application uses its signed, authenticated, bounded upload endpoint and an ACL-free PutObject for originals/derivatives. The upload is limited to 10 MiB and checked against declared byte size and SHA-256. Read, delete and recover through the same private disk. Web and worker share credentials in one container. Test a real R2 upload, derivative, retrieval, deletion and restore before acceptance; no R2 round trip is verified. Do not expose the bucket publicly; `CATALOG_MEDIA_ORIGIN` is the owned HTTPS application origin for controlled derivative responses. Container storage is ephemeral.

Resend SMTP is the preferred transactional provider; use `MAIL_MAILER=smtp` and private provider host/port/username/password plus approved sender/reply-to. Do not put these in Git or build args. Keep `TRANSACTIONAL_EMAIL_ENABLED=false` until SPF/DKIM/DMARC, real invitation/reset/order/shipping delivery, bounce/retry and suppression behavior are tested. Recovery mail and transactional outbox use the database queue without synchronous fallback. Local Mailpit/array behavior is unchanged and forbidden in production.

Keep `PAYSTACK_MODE=test`, `PAYSTACK_LIVE_APPROVED=false`, `PAYMENTS_ENABLED=false`, `REFUNDS_ENABLED=false` initially. After protected pre-launch configuration, enable TEST deliberately and verify redirect, signed/duplicate/late webhook, reconciliation and refund TEST where offered. The signed webhook inbox is authoritative. LIVE credentials, real charges, refund activation and removal of the pre-launch gate require separate explicit owner approval.

## Security and deployment order

Set `APP_ENV=production`, `APP_DEBUG=false`, `LOG_CHANNEL=stderr`, a retained private `APP_KEY`, exact HTTPS origins, host-only Secure/HttpOnly/Lax encrypted sessions, private renderer key, and `PRELAUNCH_GATE_ENABLED=true` with bcrypt hash stored only in Render. Health and signed webhook paths have narrow gate exceptions. Never put credentials in `render.yaml`, source, logs or Docker build args. `SITE_URL` and `CSP_ASSET_ORIGINS` are public build settings; changing them requires rebuild. Test cookie/CSRF/HTTPS, forwarded scheme and rate limits behind actual Render ingress. Nginx access logging is off to avoid token URLs; alert on failed jobs, queue age, overdue scheduler scans, payment/notification holds, HTTP health, database capacity and backup freshness.

Before provisioning, obtain a reviewed clean `main` SHA with green hosted CI; complete Docker/Supervisor/resource/PostgreSQL load tests; verify R2/Resend/Paystack TEST accounts and private configuration; confirm region/data handling, billing, backups/PITR and a restore drill. Then, only after a separate deployment go-ahead, create the private database and web service from the approved Blueprint, supply secrets in Render, keep auto-deploy off and gate on, run migrations, readiness and protected UAT. Use the [environment checklist](../production/production-environment-checklist.md), [launch runbook](../production/launch-runbook.md) and [rollback runbook](../production/rollback-runbook.md). Do not provision Render during this conversion.
