# Phase 3O — Render topology optimization proposal

> **Superseded 2026-10-04:** The business owner approved the [ultra-lean one-web/one-PostgreSQL topology](render-ultra-lean-proposal.md), and its configuration has been applied to `render.yaml`. This one-Key-Value proposal remains historical comparison only. Nothing has been provisioned.

Date: 2026-10-04. **Historical proposal only; no resources provisioned.** The current [Render runbook](render-production.md) and Blueprint use the approved ultra-lean design. This earlier one-Key-Value proposal is retained for comparison, not application; its obsolete patch file is excluded from the release.

## Decision for review

Use one Frankfurt Docker web service running Nginx, PHP-FPM, and standalone Next.js; one 512 MB worker; one minute cron; PostgreSQL 18; and **one** 256 MB persistent `noeviction` Key Value for queues only. Keep sessions and cache in PostgreSQL. Keep private S3-compatible media and transactional SMTP external. The private PostgreSQL URL is injected through `fromDatabase.connectionString` into `DB_URL`; the private Key Value URL through `fromService.connectionString` into `REDIS_URL` on web, worker, and cron. The Blueprint retains `ipAllowList: []` for both datastores. The web tier stays 2 GB until a measured 512 MB container test passes.

Render's internal PostgreSQL certificate is self-signed. `DB_SSLMODE=require` enforces TLS, while `verify-ca` and `verify-full` are unsupported on this connection. `PRODUCTION_NETWORK_PROFILE=render-private` is guarded in the application by Render's runtime markers, PostgreSQL URL/TLS, database cache and limiter, and a private `redis://` queue URL. The default production profile remains `verified-tls`; local/test defaults are unchanged. No Render hostname or credential is hardcoded. The Blueprint property references, rather than URL shape alone, establish that these are internal URLs. Inspect resulting config on Render before launch without printing credentials.

Do not enable external database/Key Value access for normal service traffic. For emergency off-platform PostgreSQL administration, an authorized operator can temporarily add the specific operator egress IP as a `/32` in the Render dashboard, use Render's external URL with certificate verification, record the access window, then remove the allowlist entry. The app continues using its private URL. Internal Key Value authentication is optional: a dedicated production workspace/environment and no external allowlist are sufficient for the initial small deployment; enable internal auth before launch if unrelated services share the private network or policy requires it. Enabling it later restarts the instance and needs an authenticated URL rollout.

## Cache and queue correctness

Database cache has an active migration for `cache` and `cache_locks`, plus hourly expired-row cleanup. The default rate limiter and encrypted, ten-minute MFA enrollment secret use the selected cache store. The production proposal selects database cache and limiter, leaving the queue as the only Key Value tenant. This avoids sharing a `noeviction` memory pool with cache growth. PostgreSQL cache writes, cleanup, disk and connection pressure must be measured; increase the PostgreSQL tier before saturation. Sessions, failed jobs and transactional outbox stay PostgreSQL. The queue retains `journal-snapshot`, `noeviction`, a 90-second retry lease versus a 60-second worker timeout, 3 attempts, failed-job records and the outbox/reconciliation paths. A Redis loss can delay work but must not lose authoritative commerce state. Monitor queue memory, backlog age, failed jobs, cache table/index size and cron freshness.

## Memory and cost

The experimental [PHP-FPM profile](../../docker/render/php-fpm-low-memory.conf) caps workers at two, with one warm child and recycling at 200 requests. It is **not wired into the image** pending container testing. Standalone Next.js is already built without dev tooling in `Dockerfile.render`. A prior local macOS loopback run of standalone Next after basic page requests used about 87 MiB RSS; a PHP Artisan bootstrap used about 47 MiB RSS. These are process baselines, not Linux image peaks, PHP-FPM request peaks, simultaneous traffic or image derivative processing. With Nginx, Supervisor, Node, two PHP children, allocator overhead and SSR spikes, 512 MB is **MARGINAL / NOT YET APPROVED**. The current 2 GB web tier is **SAFE for initial memory headroom**, subject to normal production/load validation. Docker is unavailable in this environment; run a Linux container at a 512 MB hard limit with production environment, warm catalog/auth/cart routes, simultaneous requests, memory and restart/OOM tracking before downgrading. Test payment/webhook bursts and upload/derivative jobs on the separate worker. Do not impose a Node heap cap until SSR behavior is measured; a heap cap alone does not bound RSS.

## Object storage and email

Prefer a private Cloudflare R2 Standard bucket for the initial catalogue: S3 API, no R2 egress charge, 10 GB-month/1M Class A/10M Class B monthly free tier, then $0.015/GB-month plus operations. A 50 GB-month example is about $0.60 storage beyond the free 10 GB, before billable operations and version history. Backblaze B2 is lower per GB ($6.95/TB-month, first 10 GB free) and has free transactions but egress is normally free only up to 3× average storage; it is a reasonable alternative if actual traffic fits. AWS S3 has broadest operational tooling but regional storage/request/egress charges are more complex. This application proxies private media through Laravel, so Render outbound bandwidth may still be billable even when R2 egress is free. Keep the current S3 abstraction; test scoped web/worker credentials, upload/presign/derivative/retrieval/delete, versioning, independent backup/restore and lifecycle cost before selecting a provider. Do not make the bucket public.

For small transactional volume, prefer Resend SMTP Free initially ($0, 3,000/month **and** 100/day); upgrade to Pro ($20/month, 50,000/month) if alerts or demand exceed the daily cap. Postmark has a 100/month free developer plan and Basic $15/month for 10,000; SES Essentials is about $0.16/1,000 plus data charges but requires more AWS identity, deliverability and sandbox operations. Verify domain SPF/DKIM/DMARC, sender approval, real inbox delivery, bounces and retries before enabling production mail. Marketing mail is outside this choice.
