# Phase 3N product management simplification report

Version 1.0 — 2026-09-27. Phase 3N remains **OPEN** for client UAT; Phase 3O has not begun. This report records developer remediation and a real local Chrome owner workflow, not client acceptance. The [flow proposal](phase-3n-product-ux-proposal.md) was written before implementation. ADMIN-UX-018–021 are tracked in the [defect register](../uat/02-defect-register.md).

1. **Previous workflow problems.** The existing product editor mixed business details with tax setup, labelled the simple SKU/price as a variant, exposed media position/processing details, and sent owners to an unfiltered inventory list. The local database had no active configured tax treatment, so valid drafts could not be published. Existing backend publication, price, inventory, and tax checks were kept.

2. **Final creation flow.** Products → Add Product → name, description, category and product type → Save and continue → SKU and NGN price (or guided option combinations) → Images → Inventory → readiness review → Publish product. A name-only incomplete draft still saves. Editing uses the same four non-rigid tabs. Save status states Saving, Saved, Unsaved changes, or a failure with retained form values.

3. **Information architecture.** The four tabs are **Details**, **Pricing & Variants**, **Images**, and **Inventory**. Details presents ordinary business fields first and places tax treatment under **More settings**. Product status/readiness remains in a separate panel. Products back navigation and separated Archive/Restore controls are preserved.

4. **Pricing UX.** Simple products show one **SKU and price** form, without option-combination controls. Prices are entered/displayed in NGN, including correctly grouped examples such as ₦4,500.50, then converted exactly to integer kobo; malformed grouping is rejected. Variant products use named options, comma-separated values, generated combinations, and SKU/price rows. Variant generation has automated coverage but was not exercised end-to-end in live Chrome during this pass.

5. **Tax-treatment resolution.** The backend still requires a tax treatment resolvable in the current validated bundle at publication; checkout independently requires an active complete calculation bundle. Drafts may be incomplete. A sole configured treatment is assigned on save; multiple configured treatments require a controlled selection. Existing mismatched references are not silently remapped.

6. **Development tax configuration.** `cd backend && /opt/homebrew/bin/php artisan catalog:configure-local-tax` was run against the native local database with an existing owner. It published the immutable, audited, `development_only` configuration `local-uat-20260927160248-512457`, containing a sole `STANDARD` treatment labelled “Standard tax treatment.” The example 10% product/delivery rates and ₦5.05 Lagos delivery are **DEVELOPMENT / TEST ONLY — NOT PRODUCTION TAX POLICY**. The command is local/testing-only, idempotent when an active bundle exists, and uses the established configuration service. Production still rejects development-only configuration and needs client/accounting approval. See [tax guide](tax.md).

7. **Publication result.** Through the normal Chrome admin UI, the existing local test product `spoon` saved its configured treatment and published; `/products` showed it and `/products/spoon` displayed its image, ₦438.00, available stock and SKU. The newly created UAT sample also published normally and its storefront detail displayed the uploaded image, ₦4,500.50, available stock, SKU and description. No direct API, database write, or guard bypass was used during the human-like workflow.

8. **Images/gallery redesign.** Product images use cards with thumbnail, first-image indicator and a labelled action menu. A single card no longer stretches across a wide desktop editor. Processing/failed statuses use plain language only where action is needed; removed images disappear from the active gallery. The image description is a labelled alt-text field.

9. **Upload/processing.** A single drag-or-choose area accepts JPEG/PNG/WebP, previews the chosen file, then reports upload/processing; bounded automatic polling refreshes the result. Live Chrome upload reached Ready without a manual refresh. After success, the selected file, description and preview are cleared to prevent accidental duplicate submission. The live success reset was covered by a frontend regression test; the browser upload happened before that final small reset fix.

10. **Ordering/removal.** The action menu lets the owner make another image main or move it left/right without entering numeric positions; the existing position API remains authoritative. In Chrome, the second image became the main image, its description changed, and the old image was removed after confirmation. The retired image did not remain in the normal gallery. Backend retirement/history behavior did not change.

11. **Inventory context.** Manage inventory carries the product UUID and SKU. A hydration-safe initialization applies the SKU filter on entry, and a validated product-specific link returns to the exact editor. Chrome retest showed only the UAT sample's row with stock 3/available 3, then returned to that product. Stock adjustment permissions and ledger remain unchanged.

12. **Draft/publish behavior.** Name-only drafts can be saved with incomplete image, stock and tax setup. Readiness reflects backend publication issues. Publication required description, active category, active SKU/price, ready image and current configured tax treatment. Stock was initialized for UAT but is not a publication prerequisite; positive available stock controls browse/search visibility.

13. **Archive/restore.** The UAT sample was archived through the owner UI, then restored. Chrome showed **Draft** after restoration; it was not republished automatically. The final local UAT sample is Draft with three units of stock, one temporary brand image and a saved revised price of ₦4,750.00. It is not a real merchandise listing. The existing `spoon` test product remains Published locally.

14. **Responsive/accessibility review.** Chrome responsive screenshots were inspected at **320, 375, 768, 1024 and 1440 px** for the product editor/gallery. Tabs, form, gallery card, upload area and status panel fit the page; the status panel stacks on narrow screens and the image remains proportionate. At 320/375 the tabs wrap into two rows. No full-page horizontal overflow was observed in these screenshots; this was a visual inspection, not a computed scroll-width measurement. The tab group exposes tab/tabpanel semantics and Right/Left keyboard navigation worked in Chrome. The gallery actions button was keyboard focusable, Escape closed its menu and returned focus, labels/alt descriptions were exposed, and readiness used text as well as styling. A full screen-reader, contrast-ratio and reduced-motion audit was not performed in this pass. Chrome's development overlay showed a hydration warning; the visible excerpt did not establish whether it came from the application or a browser extension, so this remains an investigation item rather than a claimed product defect.

15. **Backend checks.** Isolated PostgreSQL `ConfigureLocalCatalogTaxTest`: **1 test / 9 assertions passed**. Catalog/checkout/tax regression: **55 tests / 1,234 assertions passed**. Targeted Pint and Larastan passed. `composer audit --locked --no-interaction` was attempted but **NOT VERIFIED** because `repo.packagist.org` DNS was unavailable.

16. **Frontend checks.** ESLint, Prettier and standalone TypeScript passed. Full Vitest: **21 files / 218 tests passed**. The final Next.js `next build --webpack` compiled, TypeScript-checked and generated all 28 static pages successfully. One intermediate TypeScript run overlapped that build and saw its generated `.next/types` files being replaced; a sequential recheck passed. `npm audit --audit-level=high` was attempted but **NOT VERIFIED** because `registry.npmjs.org` DNS was unavailable. The standard Turbopack build could not bind a sandbox worker port; webpack is the verified production build path in this environment.

17. **Complete human-like UAT.** In Chrome as the authenticated, MFA-verified Business Owner: (1) Products, (2) Add Product, (3) name, (4) description, (5) category, (6) Simple product, (7) SKU `UAT-SAMPLE-20260927`, (8) ₦4,500.50 price, (9) temporary logo upload with alt description and automatic processing, (10) opening stock +3 with reason, (11) all readiness items Ready, (12) Publish, (13) storefront detail/image/price/stock/SKU, (14) return to edit, (15) save revised ₦4,750.00 price, (16) Manage inventory, (17) exact-product return, (18) Archive, (19) Restore to Draft. Each step was observed through the UI. The revised price was confirmed saved in the editor; a second storefront price check after that edit was not performed before archive.

18. **Defects and remaining gates.** ADMIN-UX-018–021 are **fixed with developer retest passed**; client retest/acceptance is pending. The new UAT sample and `spoon` are local test content. Replace the temporary logo and confirm real product descriptions/photos, pricing, tax and delivery policy before production. External provider setup, staging validation, security/operational gates and formal business UAT sign-off remain Phase 3N dependencies. No production tax configuration was changed.

Final frontend validation: lint PASS; formatting PASS; TypeScript PASS; Vitest **218/218 PASS**; webpack production build PASS.
