# Render ultra-lean rollback and recovery

No Render rollback has been executed. Rehearse before public launch with named business and technical decision owners. This applies to **one Docker web service plus one PostgreSQL database**; queue, cache, sessions and commerce data all share that database.

1. **Contain:** disable payments and keep/re-enable `PRELAUNCH_GATE_ENABLED=true` when correctness is uncertain. Do not blindly cancel/refund provider transactions. Record incident time, current/previous approved SHA, migration version, affected orders, pending webhook inbox/outbox/jobs/failed jobs and recent logs without secrets.
2. **Code/config rollback:** manually redeploy the last known-good **web image** from an approved SHA, with its matching environment and public build settings. Auto-deploy remains off. Supervisor then starts Nginx, PHP-FPM, Next, one worker and scheduler together. If the prior code cannot read the new schema, stop writes and use a reviewed forward fix or compatible migration plan; do not assume image rollback undoes database changes.
3. **Queue and scheduler:** after replacement, inspect `supervisorctl status`, `php artisan app:readiness`, queue age, failed jobs and overdue scans. A job interrupted during shutdown becomes eligible after its 90-second reservation lease; replay is at least once. Existing payment, inventory, refund and notification idempotency/fencing must prevent duplicate business effects. Old/new containers may overlap; shared database `onOneServer()` locks and `withoutOverlapping()` protect scheduled work. Confirm one effective scheduler and no orphaned workers.
4. **Database recovery:** do not run `migrate:fresh`. Take a fresh backup and reconcile Paystack/payment/order state before any restore. A PITR restore to a new database needs explicit owner approval for its recovery point and possible data loss. Repoint the sole web service's private `DB_URL`, run read-only reconciliation, then controlled smoke tests. Restoring PostgreSQL also rewinds jobs, cache and sessions; do not treat a recovered queue as exactly-once. Inspect webhooks/outbox and reprocess only through existing idempotent commands.
5. **Media/email/provider recovery:** restore private versioned R2 objects and reconcile media DB references; verify derivative reads. Rotate/revert Resend settings if needed. Reconcile Paystack provider records with PostgreSQL before re-enabling TEST or LIVE checkout; do not replay a refund or charge merely because a job appears failed.
6. **Verify/resume:** check storefront, admin MFA, secure cookies/CSRF, database readiness, Supervisor status, queue/scheduler freshness, R2, email, backups and relevant TEST payment path. Record operator/owner acceptance before gate removal or payment reactivation.

Render PITR, R2 recovery, process restarts, full container restart, deployment overlap and end-to-end replay remain **NOT VERIFIED** until rehearsed. A rollback is not a substitute for compatible migrations and tested backups.
